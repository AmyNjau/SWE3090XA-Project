What it is, in one breath

Say this: "You type your symptoms. It tells you what you might have, why it thinks so, which kind of doctor to see, and where the nearest one is."

How it works (explain like this)

Think of a scorecard for each illness.

Every illness has a list of symptoms, and each symptom has a score for how strongly it points to that illness. Fever points strongly to malaria (0.9). Headache points weakly (0.5).

You tick your symptoms. For each illness I add up the scores you ticked, then divide by that illness's total possible score. That gives a percentage.

Highest percentage wins. That's it. No AI, no black box — just adding and dividing.

0.9 + 0.5 + 0.8 = 2.2 fever + headache + chills 2.2 ÷ 4.0 = 55% malaria's total possible score is 4.0
Say this: "That 55% isn't a guess from a model. It's fever plus headache plus chills, divided by everything malaria could score. I can do it on the whiteboard."

Why not AI? (they will ask)

Three reasons, in order:

  1. You can see why. Every number breaks down into named symptoms. An AI can't show its working.
  2. I have no medical dataset. Training on a small or biased one, for health, would be worse than useless.
  3. A doctor can fix it. A wrong number is a one-line change. A wrong model needs retraining.

The three layers

1. The phone app (Flutter) — collects symptoms, shows results. Does no thinking at all.

2. The server (Node/Express) — holds the scorecard logic and talks to Google Maps.

3. The data — the illness rules, and the map service for nearby clinics.

Say this: "The phone holds no medical logic. That's deliberate — I can fix a wrong rule on the server without shipping a new app, and the Google Maps key never leaves the server."

The 8 answers that cover most questions

Is it a medical device?

"No. It's guidance, not diagnosis. The disclaimer text sits in one config file, it's attached to every diagnosis response in one place in the code, and the app shows a banner on every screen with results."

Are the medical rules verified by a doctor?

"No, and I say so in the report. I curated them from public sources. Clinical review is the first thing needed before real use. That's the weakest part of the system and I know it."

How accurate is it?

"I ran 12 test cases, covering 12 of the 15 illnesses. It ranked the right one first every time. But I wrote those cases against my own rules — so it proves the maths works, not that the medicine is right."

What if someone gets hurt by a wrong answer?

"That shaped the design. It shows a ranked list, not a verdict. It shows the reasoning. It flags severity. It always sends you to a real doctor. And it says on every screen that it's guidance only."

Is it secure?

"The Maps key is server-side only, input is validated, errors never leak internals, and sign-in uses Firebase with tokens verified on the server. Not done yet: HTTPS on the dev build, rate limiting, security headers. They're written up as next steps."

How do you know it works?

"25 automated tests, all passing. The scoring engine is a pure function — no database, no network — so the riskiest part is the easiest to test. That was on purpose."

What's new about it?

"Not symptom checking on its own. It's the combination: explainable results, plus which doctor to see, plus where they are — built for a Kenyan, low-connectivity setting. No tool I reviewed does all three."

Did you write this code?

"Yes — open any file and I'll walk you through it." (Have ready: why the phone holds no logic; why the engine is a pure function; why a token is checked even when sign-in is optional.)

"Did you actually write this?"

Don't recite code. Explain why you chose it, and what you rejected. That's what only the author can do.

Offer these three files yourself — you know exactly why each is like that:

  1. The scoring engine. "It adds up weights and divides. It takes the illness list as an argument instead of loading the file itself — that's what makes it testable without a database."
  2. The app startup file. "Building the app is separate from starting the server, so tests can run the app without grabbing port 3000."
  3. The sign-in check. "If a token is sent, it's always checked — even when sign-in is optional. Otherwise a fake token would sail through."
Why do you round the score on the server?

"So every screen shows the same number. If the phone rounded it, one screen could say 54.99% and another 55%."

Why does the phone hold no medical logic?

"So I can fix a wrong rule on the server without publishing a new app — and so the Google Maps key never leaves the server."

Tell me a bug you fixed.

"Sign-in rejected every valid login because the server had no project ID set, so it couldn't check the token. It looked like a wrong password. Now it fails with a clear server error naming the missing setting instead of blaming the user."

What does this line do? (something you don't recognise)

"That's generated Flutter/Android scaffolding, not code I wrote. Mine is in lib/ and backend/src/." Never guess at generated files.
