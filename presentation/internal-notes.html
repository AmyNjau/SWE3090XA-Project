Three rules for the room.
  • Never say "it diagnoses". Say it ranks probable conditions and explains why. The whole safety story hangs on that word.
  • If you do not know, say so, then say what you would do. "I have not measured that. I would measure it by X." That scores better than a guess.
  • Own the gaps first. The limitations are already written in the report. Saying them before you are asked converts a weakness into evidence of judgement.

Slide-by-slide script

1. The problem

People self-diagnose in the dark. Kenya has a low doctor-to-patient ratio, long travel distances and out-of-pocket costs, so people delay care — often because they do not know how serious a symptom is or which practitioner to see.

The gap I am closing is not "what is wrong with me". It is "is this serious, who do I see, and where is one near me" — three questions no existing tool answers together for this market.

2–3. What I built · the stack

Flutter client, Node/Express API hosting a rule-based engine, a swappable data tier and Google Maps for location. Three tiers, one API boundary.

The client holds no diagnostic logic at all. It collects symptoms, calls the API, and renders typed models. Every piece of reasoning lives behind the API boundary — which is why I can correct the rule base without shipping a new app.

4–5. Integration + architecture

The mobile app never talks to the database or Maps directly. The API is the single integration point and mediator.

That is deliberate. It keeps the subsystems loosely coupled, it keeps the Maps key server-side, and it means the engine and the provider service are independent modules I can replace behind a stable contract.

6. Data flow

Symptoms → API → engine scores → ranked conditions + specialist → client sends specialist + coordinates → API queries Maps server-side → ranked providers → rendered with the disclaimer.

7. Security & safety

Maps key server-side only; request validation before processing; the error handler never leaks internals; the disclaimer is attached centrally in config so no endpoint can forget it; location is read only after explicit permission and denial is a supported path.

I want to be straight about what is not done: there is no TLS on the development build, no rate limiting and no security headers yet. Those are written up as concrete work items, not discovered on the day.

8–10. Demo + the rule engine

Run the demo path. Then show the scoring: sum the weights of reported symptoms, divide by that condition's maximum possible weight, filter below 0.2, sort, cap at 5.

Every score traces back to named symptoms, and the app shows them. That auditability is the core contribution — in a health context an unexplained number is either ignored or trusted blindly, and both are bad.

11–12. API surface · providers

Five endpoints. POST /api/diagnose, POST /api/providers, GET /api/symptoms, GET /api/specialists, GET /api/health.

13–15. Testing · data model · challenges

25 automated tests. The engine is a pure function specifically so the highest-risk component is the easiest to test. Seven entities; the associative entity carries the rule weight, which is what makes the base tunable without schema change.

16–17. Outcomes · what's next

Objectives met; accuracy assessed on 12 vignettes (12/12 first). Next: security hardening, Firestore persistence, clinical review, user testing.

Backend architecture — likely questions

Walk me through what happens when I press Analyse.

The client POSTs {symptoms:[...]} to /api/diagnose. validateDiagnoseBody middleware checks the body and 400s if it is malformed. The route calls runDiagnosis in diagnosisService.js, which loads conditions from whichever data store is configured, calls the pure diagnose() engine, maps symptom ids to display names for the explainability chips, looks up the specialist for the top condition, writes an anonymised query-log entry, and returns results plus the central disclaimer. Errors go to next(err) and the central error handler.

Why Node and Express rather than something heavier?

The workload is I/O-bound orchestration — receive JSON, score in memory, call one external API, return JSON. Node suits that, has zero build step for CommonJS, and the whole team is one person, so an unopinionated framework kept the moving parts visible. Nothing in the design depends on Express; the routes are thin.

Why is app.js separate from server.js?

createApp() builds the Express app without binding a port, so tests import the app and start it on an ephemeral port. server.js is the only thing that binds 3000. That separation is what makes the integration tests possible without port conflicts.

Explain the repositories folder.

It is a factory returning a configured singleton data store. localDataStore.js is file-backed; firestoreDataStore.js is a documented stub whose method signatures match exactly. Swapping DATA_STORE=firestore changes the implementation without touching engine, service or route code. That is the dependency-inversion idea applied at the data tier.

Is Firestore actually working?

No, and the report says so. It is a stub that throws in its constructor with a message telling you to set DATA_STORE=local or implement it. The interface is real and matched; the implementation is the next data-tier task. I would rather ship an honest stub than a half-working store that loses queries.

Where does configuration live?

Every environment read is in config/index.js — port, data store, provider source, Maps key, auth settings, engine thresholds, and the disclaimer text. One file to audit. Nothing else in the codebase reads process.env.

The rule engine — expect the most questions here

Show me the scoring code and explain it. 
function scoreCondition(condition, userSymptoms) {
  const weights = condition.symptoms || {};
  const maxScore = Object.values(weights).reduce((a, b) => a + b, 0);
  if (maxScore <= 0) return { score: 0, matched: [] };

  let matchedWeight = 0;
  const matched = [];
  for (const symptom of userSymptoms) {
    if (Object.prototype.hasOwnProperty.call(weights, symptom)) {
      matchedWeight += weights[symptom];
      matched.push(symptom);
    }
  }
  return { score: matchedWeight / maxScore, matched };
}

Sum the weights of what the user reported that this condition cares about, divide by everything this condition could contribute. Normalising by the maximum is what makes a 7-symptom condition comparable with a 3-symptom one.

Why hasOwnProperty.call instead of weights[symptom]?

Guarding against prototype keys. If a user sent "constructor" or "toString" as a symptom id, a naive in or truthiness check could match something inherited from Object.prototype and pollute the score. This is a small hardening detail, and a good one to point at if they push on input safety.

Why rule-based and not machine learning?

Three reasons. Explainability: every score decomposes into named symptoms, which I can show the user and you can audit. Data: I have no labelled clinical dataset, and training on a small or biased one in a safety-sensitive domain would be worse than useless. Correctability: a wrong weight is a one-line fix by a clinician; a wrong model is a retraining exercise. I would revisit this with real data and a hybrid that keeps the rules as a floor.

Where do the weights come from? Are they clinically validated?

They are curated by me from public symptom descriptions, on a 0–1 scale where the number expresses how strongly a symptom indicates that condition. They are not clinically validated — the knowledge base says so in its own metadata, the app says so on every response, and the report says so in the limitations. Clinical review by a qualified practitioner is the first item before any real use.

Why threshold 0.2 and max 5?

Both are configuration, not magic. 0.2 keeps out conditions matched by a single weak symptom, which otherwise produce a long tail of alarming noise. Capping at 5 is a user-experience decision — a ranked list longer than that stops being actionable. Both live in config/index.js and can be tuned without touching the engine.

Is the engine deterministic?

Yes, and there is a test named for it — "diagnose is deterministic for the same input". It is a pure function of its arguments: no clock, no randomness, no I/O. That is what lets me promise the reliability requirement rather than hope for it.

What if I enter symptoms that match nothing?

Unknown ids contribute nothing — there is a test for that. If no condition clears the threshold you get an empty ranked list with the specialist null and the disclaimer still attached. The client shows an empty state rather than an error, because "nothing matched" is a legitimate answer.

What if the same symptom is submitted twice?

Input is de-duplicated with a Set before scoring, so a duplicate cannot inflate a score. Also a named test.

How accurate is it?

I ran 12 symptom vignettes, one per condition, through the real engine: the expected condition ranked first in 12 of 12. I am careful about what that means — I wrote the vignettes against the same knowledge base, so it measures internal consistency, not clinical accuracy. It proves the weighting and ranking behave as designed. Only clinical review proves the rules are right.

The API surface

Why POST for diagnose rather than GET?

The request carries a symptom set, which is health information. A GET would put it in the URL, where it lands in server logs, browser history and proxies. POST keeps it in the body. It is also unbounded in length, which URLs are not.

How do you validate input?

middleware/validate.js runs before the handler. validateDiagnoseBody requires symptoms to be a non-empty array; the providers validator requires a specialist and numeric coordinates. Failures return 400 with a clear message. Two tests cover the 400 paths.

Be honest if pushed: radius and limit are not yet clamped, and the symptoms array is not length-capped. Those are on the hardening list.

What does the client see when the server errors?

A generic message. The central error handler returns a safe payload on 5xx and never echoes stack traces or internal detail. The client turns any failure into a readable message with a retry, which is acceptance test T5.

Why is /api/health there?

Liveness. The test suite asserts it, and any real deployment needs a probe. It reports which data store and provider source are active, which makes "which mode is this running in" answerable without reading the environment.

Data, providers and location

How are nearby providers found?

Two interchangeable sources chosen by PROVIDER_SOURCE. mock ranks the 12 bundled records by haversine distance from the user. google calls Maps Nearby Search server-side using the specialist's search keywords, then caches the response. Both satisfy the same interface, so routes and client are identical either way.

Why haversine?

Great-circle distance on a sphere. At city scale it is accurate to well within the error of a phone's GPS fix, and it needs no external call. Road distance would be better for a user but requires a Directions request per provider, which is billable and slow.

Why cache provider lookups?

Cost and latency. Maps Nearby Search is billed per call, and two users in the same area asking for the same specialty want the same answer. A five-minute TTL keyed on specialist plus rounded coordinates cuts repeat calls without serving stale results.

Known gap: the cache is an unbounded Map with no eviction, so it grows. Adding a size cap is on the list.

What happens if the user denies location?

The flow continues. The app falls back to Nairobi coordinates and shows a banner saying it is using a default location, so the user still gets symptom and specialist guidance. That is acceptance test T4 and an explicit functional requirement — denial is a supported path, not an error.

What is stored about the user?

A query-log entry: a generated id, the symptom set, the top condition, the recommended specialist, a timestamp, and — if signed in — the Firebase uid. No name, no email, no coordinates. That is deliberate minimisation. The log is currently in memory and is lost on restart.

Authentication (newest work — expect questions)

How does sign-in work end to end?

Firebase Authentication with email and password. The app signs in through the SDK and gets an ID token, which is a signed JWT. Every API call carries it as Authorization: Bearer <token>. The backend verifies it with the Firebase Admin SDK and attaches {uid, email} to the request. AuthGate listens to the auth stream and decides whether to show sign-in or the app.

Why verify with the Admin SDK instead of decoding the JWT yourself?

Because verifying a token properly means checking the signature against Google's rotating public keys, plus issuer, audience and expiry. Hand-rolling that is exactly how token verification gets silently weakened — you end up decoding without verifying and accepting anything. The SDK does the rotation and the checks.

You have an AUTH_REQUIRED flag. Isn't optional auth insecure?

This is the detail I would most like to be asked. The rule is: a token that is supplied is always verified, whatever the flag says. The flag only decides whether a request with no token is allowed through anonymously. If it worked the other way, a forged token would be accepted in the default configuration. There is a test named for exactly that case — "a supplied token is verified even when auth is optional".

Why are the catalogue endpoints still public?

The symptom and specialist lists are needed to render the app before anyone has a token, and they contain no user data. Everything that reasons about a person's symptoms sits behind authentication.

What does the error say when a token is bad?

"Authentication token is invalid or has expired." Deliberately vague — the SDK's message can describe why a token failed, which is more than an unauthenticated caller should learn. There is a test asserting the reason never leaks.

Is history per user now?

Yes on the client: history is keyed by uid, so signing out and in as someone else never shows the previous account's checks. On the server the uid is recorded on each query-log entry. Full per-user persistence needs the Firestore store, which is the next task.

Your Firebase API key is in the repository. Isn't that a leak?

No. An Android Firebase API key identifies the project and is restricted by package name and signing certificate; Google ships it in google-services.json by design. The key that is sensitive — the Maps Platform key — is server-side only and never reaches the client. If you want defence in depth on the Firebase side, the answer is App Check plus key restrictions.

Security — answer these honestly

Do not overclaim here. The report already lists these gaps; matching it exactly makes you look rigorous rather than caught out.
Is the traffic encrypted?

Not in the development build — it talks to a local backend over HTTP. The architecture assumes HTTPS and the production requirement is TLS with certificate validation. I list it as a limitation rather than claiming it is done.

What stops someone hammering your API?

Nothing yet, and that matters most in PROVIDER_SOURCE=google mode, where each call is billable. Rate limiting on the unauthenticated endpoints is the first hardening item, along with an origin allowlist for CORS, security headers via helmet, clamping radius and limit, and capping the symptoms array.

Where is the Maps key?

Server-side in an environment variable, read once in config/index.js. Every Maps call is made by the backend. The client never sees it — that is the main reason the provider lookup is an API endpoint rather than a direct call from the app.

Is this GDPR/DPA compliant?

I have applied data minimisation and explicit consent for location, which are the right instincts, but I would not claim compliance with Kenya's Data Protection Act without a review. Health data is sensitive personal data; a real deployment needs a lawful basis, a retention policy, a subject-access route and a DPIA. Right now the log holds no identifiers beyond a uid.

Testing

What do you actually test?

25 automated tests. Nine unit tests on the engine cover the scoring bounds, normalisation, unknown symptoms, ranking order, threshold filtering, explainability output, determinism, de-duplication and the result cap. Six integration tests drive the HTTP API including both 400 paths. Ten cover authentication — valid token, forged token, forged token while auth is optional, anonymous allowed and rejected, public catalogue, malformed header, uid on the log, and the message-leak check.

Why is the engine a pure function?

So the component with the highest consequence of being wrong is the one that is trivial to test — no server, no database, no emulator. It is a design decision in service of testability, and it is why the engine has nine tests rather than one.

What is not tested?

The error handler, cache expiry, the live Google provider path and the Flutter UI. I would add a mocked-fetch test for the Google path and widget tests for the results screen next, plus CI so every change runs them.

Mobile client

Why Flutter?

One codebase, Android first with iOS reachable without a rewrite, and a widget model that made the explainability chips and the tabbed shell quick to build well. The portability requirement was explicit from the midterm.

How does the app talk to the backend?

Through ApiService, the single point of contact. It attaches the ID token, posts JSON, and maps responses into typed models. Errors funnel through one _decode helper that raises ApiException with a user-safe message, which is why the UI can always show something readable with a retry.

Why does the client hold no logic?

Three reasons: the rule base can be corrected server-side without an app release; the engine is testable without a device; and it keeps a single source of truth, so a phone that has not updated cannot disagree with the server about what a symptom means.

The hard ones

Is this a medical device?

No, and I have been careful not to build one. It offers guidance, not diagnosis. The disclaimer is attached centrally in configuration so no response path can omit it, and it appears on every result screen. A medical device would need clinical validation, a regulatory pathway and a quality system — none of which this has, which is precisely why the language throughout is "probable conditions" and "guidance".

What if someone acts on a wrong answer and is harmed?

That is the risk that shaped the design. The mitigations are: ranked probabilities rather than a single verdict, the reasoning shown so the user can judge it, severity carried through so high-severity conditions are emphasised, a disclaimer that cannot be forgotten, and routing to a human specialist as the recommended action. The tool's job is to get someone to the right clinician sooner, not to replace one. The residual risk is why clinical validation is the first recommendation.

What would you do differently?

Two things. I would get clinical review of the knowledge base earlier — it is the input everything else depends on, and it is the one thing I could not validate myself. And I would set up CI from the first commit; I have 25 tests but nothing forces them to run, so their value depends on me remembering.

What is the weakest part of this system?

The knowledge base, without question. The engineering around it is sound and tested; the rules inside it are educated curation, not clinical evidence. Everything downstream is only as good as those weights, which is why I state it as a limitation rather than burying it.

How would this scale to 100,000 users?

The API is stateless, so it scales horizontally behind a load balancer. The engine is in-memory and sub-millisecond, so it is not the bottleneck. The real constraints are the Maps quota and cost — which is what the cache exists for, and I would add a shared cache such as Redis instead of a per-instance map — and Firestore read volume for the knowledge base, which I would cache in memory since it changes rarely.

What is genuinely novel here?

Not the symptom checking on its own. It is the combination: explainable rule-based inference, specialist routing, and location-aware provider recommendation, in one flow, built for a low-connectivity developing-region context. The comparison table in the report shows no reviewed system does all four.

Did you write this code?

Yes — and be ready to prove it by opening any file they name and explaining a design decision in it. Good ones to offer: why hasOwnProperty.call is in the scoring loop, why createApp() is separate from server.js, and why a supplied token is verified even when auth is optional.
